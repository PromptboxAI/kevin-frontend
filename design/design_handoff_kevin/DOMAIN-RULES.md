# CLAUDE.md — kevin.co

Persistent project context for Claude. Read this first.

---

## What this is

**Kevin** (kevin.co) is a B2B SaaS prototype for **insurance content-inventory adjusters and estate liquidators**. Adjusters drop a folder of damage photos; Kevin identifies each item, matches make/model, picks a content class, suggests depreciation, and pulls three live retailer price comps — producing a defensible personal-property inventory the adjuster reviews and exports to Xactimate.

This is a **high-fidelity design prototype**, not a production app. It exists to communicate the intended product to engineering. Most buttons are visual-only by design (see "Static vs. wired" below).

The deliverable is the `pages/` folder — one standalone HTML file per screen — plus the shared component library and stylesheet.

---

## Tech stack & architecture

- **React 18 + Babel Standalone, loaded inline from CDN.** No build step, no bundler, no npm. Pinned versions with integrity hashes (do not bump or unpin).
- **One shared stylesheet:** `kevin.css` (~2000 lines). All visual styling lives here. Components use `className`, almost never inline styles for layout primitives (some inline styles exist for one-offs).
- **Components** live in `components/*.jsx`, each loaded via `<script type="text/babel" src="...">`.
- **Each `pages/NN-Name.html`** is a thin standalone wrapper: it loads fonts + `kevin.css` + the full component script chain, then mounts ONE component into `#root`. These are the handoff artifacts.
- **`Kevin.html`** is the master design-canvas file (all artboards on a pan/zoom canvas via `design-canvas.jsx`). Useful for review; `pages/` is the source of truth for individual screens.
- **`Kevin-print.html`** renders every artboard one-per-page for PDF export.
- **Responsive scope:** the app is **desktop-first** — the tool surfaces (worksheet, estate worksheet, settings, carrier profiles, admin console 64–72, claim overview/photos/audit, exports history) intentionally stay desktop-width; field work has dedicated mobile pages (11/26/27/28). The **marketing + auth pages ARE responsive** (landing, pricing, product, segment, about, contact, docs, legal, security, careers, sign-in, forgot/reset, account-create, 404) via a `@media` block at the end of `kevin.css` (≤1080/≤820/≤520px) that collapses `.k-hero`/`.k-tiers`/`.k-auth`/`.k-docs-body` grids, hides the `.k-nav` middle links + `.k-auth-r` brand panel, and stacks `.k-cta` actions. Keep new marketing/auth layout class-based (not inline-sized) so these breakpoints keep working.

### Critical constraint: global scope is shared
Every `<script type="text/babel">` shares one global scope after transpile. **Every top-level `const`/component name must be globally unique across all component files.** Name collisions silently break the app. Examples already in place: `CARRIER_STATUS_BADGE` (not `STATUS_BADGE`, which collided), `BOOK_SECTIONS`, etc. Components are exposed via `Object.assign(window, {...})` or `window.X = X` at the end of each file, and consumed as `window.ComponentName`.

When adding a component: give it a distinctive name, export it on `window`, add its `<script>` tag to both `Kevin.html` and any `pages/` wrapper that needs it.

## Domain rules — DO NOT VIOLATE

These are real product/business constraints the stakeholder locked. Getting these wrong misrepresents the product.

1. **Photo-to-item ratio:** the vision tech reads **one item per photo** — a single photo backs **at most one** item (never a photo yielding "8 items"/"12 items"). Items are always **≤ photos**, never more, because some photos are context shots, barcode/model-number close-ups of an item already counted, unmatched/blurry, or duplicates. The canonical demo claim = **60 photos → 57 items** (57 matched · 3 context) — real pack-out captures in `assets/claim/` (900px web copies in `assets/claim/web/`, sourced from PromptboxAI/Sample-photos-2). On the Photos tab (`claim-photos.jsx`), per-photo item count is 0 or 1 and the detail panel shows the single item that photo backs. Never show a claim producing more items than photos.
2b. **The .xlsx contains STATIC VALUES ONLY — never a formula.** Xactimate's importer breaks on them, and the file exists to be ingested. Every derived cell (Ext. Cost, RCV+Tax, $ Depr., ACV, totals) is written as the computed number. All recalculation happens in the web UI; the export is a snapshot of what it produced. Also: rows the backend leaves `needs_manual` may arrive with **empty-string** `desc`/`mfr`/`model` (reason `no_query` — Vision would not corroborate the OCR, and a hallucinated description on a carrier-facing document is worse than a blank). Render blanks as editable placeholders, never as an error.

2. **Xactimate uses Excel, not XML.** Xactimate/XactContents imports a pre-formatted **.xlsx** template (and uses .ESX archives for whole estimates). Programmatic integration is via XactAnalysis API/webhooks. **Never** say "Xactimate XML" anywhere. Export label is "Xactimate (Excel) · .xlsx · XactContents template."
3. **Real carriers only.** Use real insurer names (Allstate, State Farm, Nationwide, Travelers, Chubb, Liberty Mutual, USAA, GEICO, Amica, AIG, SageSure, Narragansett Bay, AFICS). The canonical demo claim's carrier is **Allstate**. Never invent fake carriers (no "Heartland Mutual" etc. — these were scrubbed). **Kevin has no special tie to Allstate** — never imply a partnership ("Allstate defaults," etc.).
4. **No direct carrier-portal submit.** Kevin exports a file the adjuster sends (download / share link / email); it does NOT push directly into carrier systems, and Kevin has **no carrier-facing review surface**. (An earlier `30-Carrier-portal.html` mocking what a carrier sees after import was **deleted** — it misrepresented the product by implying Kevin owns a carrier review tool. Don't reintroduce it.)
5. **No internal chat / @mentions / shared-notes thread.** Deemed over-engineering for MVP and removed. The **audit log stays** (who-changed-what-when = compliance/defensibility, core to the product) but it is a single-pane timeline, not a collaboration tool.
6. **Special-limits classes** (Jewelry, Firearms, Fine Arts, Furs) get amber flagging in the worksheet — flagged, never blocked. The adjuster can always override.
7. **SOC 2 Type II** is NOT claimed — the company isn't certified yet. Use concrete security language instead ("AES-256 at rest", "TLS 1.3 in transit"). SOC 2 was removed site-wide; don't reintroduce it.
8. **Abbreviations:** depreciation shortens to **"Depr."** (not "Dep").
9. **Pricing = flat monthly, never per-seat or per-claim.** Two tiers only: **Pro ($249/mo, unlimited claims with 2,000 line items per billing month included and $0.20 per item after)** for individual independent adjusters — this is the recurring-subscription model, deliberately mirroring how users already pay for Xactimate/XactContents — and **Enterprise (custom, volume licensing on one invoice)** for carriers, TPAs, and multi-adjuster agencies. Adjusters don't buy "seats"; freelancers self-subscribe (Pro), carriers/desks buy Enterprise. The earlier Solo-per-claim ($49/claim) and Agency-per-seat ($449/seat/mo) tiers were **scrapped** — never reintroduce per-claim or per-seat language, seat grids, or a 3-tier table. Pricing page (`21-Pricing.html` / `pricing.jsx`) and the Billing settings page (`settings-pages.jsx` → `SettingsBilling`) must stay in sync; the demo customer (Mariana Reyes) is on **Pro**. **ITEMS are the metered dimension, not claims.** An item costs ~$0.08 to produce, so 2,000 included items cost $160 against $249; two 2,000-item inventories in a month would be underwater at a flat price, which is why the allowance exists. Overage is $0.20 — 2.5× cost. Do not raise the allowance or drop the overage without redoing that arithmetic, and do not re-describe the plan as simply 'unlimited': claims are unlimited, items are not. **ESTATE SALES ARE PRICED SEPARATELY at $249 per estate, from the first estate.** An estate runs hundreds to thousands of items, so a single one on a flat monthly plan costs more to run than the plan collects. This is the one sanctioned per-engagement price; it is not a reintroduction of the scrapped per-claim tier.

9b. **The trial is METERED, never timed: 250 free items, no deadline.** The 7-day free trial was **scrapped** — a time box priced the trial in *calendar days* while the cost is incurred in *items*, so a throwaway signup could burn a full 2,000-item allowance (~$160 of API spend) inside the window. 250 items caps that exposure at ~$20 and lets a real adjuster take as long as they like. Never reintroduce a day count, a countdown, an expiry date, a "trial ends" email, or `trial_period_days`; a trial ends when the 250th item is produced and at no other moment. The **'first estate free' promo is also scrapped** — estates are $249 from the first one, and no surface may say otherwise. **Card is still verified at signup** (the anti-fraud step and the ads conversion event `card_added`); it is simply not charged until the account converts to Pro. 250 items is roughly four 60-photo claims, so a trial user CAN hit the cap mid-claim — which is what the truncation warning (rule 9c) exists for. Guards for all of this live in `check-domain-rules.py`.

9c. **Quota is an append-only counter, and overflow TRUNCATES rather than rejects.** Two consequences the UI must state plainly, because both generate support tickets otherwise: (a) **deleting an item does not restore quota** — the counter records items *produced*, not items *kept*, since the API spend is already incurred; every usage meter carries a note saying so. (b) When a batch would exceed the remaining allowance the backend processes **exactly up to the limit and drops the rest**, returning `truncated: true` and `dropped_count: N` rather than failing the upload. That is the one sanctioned exception to rule 21's "a failed photo is never silently dropped" — sanctioned *only* because it is never silent: the claim dashboard raises a prominent, non-dismissible alert naming the dropped count with **Add credits** / **Upgrade to Pro** beside it, so the adjuster cannot lose track of missing inventory. Dropped photos are NOT deleted from the claim (rule 22: evidence is excluded, never destroyed) — they remain, unprocessed, and run when quota is restored. Overage credits are sold in blocks at the same **$0.20 per item** as Pro overage; buying credits is never a plan change.

10. **ONE unified comp source — no per-retailer scrapers. `settings-pricing.jsx`.** Every comp comes from **Google Shopping + the Google Immersive Product API (via SerpApi)**, which already spans major retailers, specialty stores, brand-direct storefronts and marketplaces. There is no list of 18 toggleable stores, no per-store adapters/uptime, and no source-priority-by-retailer routing — those were **scrapped** when the backend consolidated; don't reintroduce them. RCV defaults to the **median of the live comps** returned for an item, alternates stay one click away in the worksheet RCV popover with a dated proof link. The Pricing settings screen controls global **valuation behavior**, not stores: *LKQ substitutions*, *enforce class depreciation ceilings*, *brand-direct tiebreaker* (used when merchant offers disagree by >15%). No domain blocklist/allowlist — not built in the backend. Three valuation bases only: (a) *Retail comp* — still sold new; (b) *Like-kind substitute* — model discontinued, priced as the nearest NEW equivalent; (c) *Manual/appraisal*.
11. **RCV always holds a NEW-replacement price; ACV is derived mathematically.** Kevin never files a used/resale price as RCV. ACV is computed by applying the claim's class-specific depreciation schedule to the retail RCV (`ACV = Ext. Cost + Tax − $ Depr.`) — there is no comparable-sale/back-solve path (`RCV = comp ÷ (1 − depr%)`), no `marketComp` field, and no resale→ACV mapping. That earlier design was **removed** when the backend consolidated on the aggregator; don't reintroduce it. Items with no confident new-replacement comp go to `needs_manual` (rule 12) rather than being priced off a used listing. Jewelry · Fine Arts · Firearms · Furs stay manual-only.
12b. **Capacity waits are not errors.** Two `manual_reason` codes — `quota_exhausted` (hourly SerpApi rate limit) and `budget_exhausted` (daily spend cap) — mean the pricing service is throttled, NOT that the adjuster must act. They render a quiet pulsing "Pricing" chip rather than the blank editable cell of a true `needs_manual`, never amber, and a worksheet bar offers **Retry N deferred** (`POST /v1/claim_items/retry-deferred`) once limits roll over. `MANUAL_KIND` in `data.jsx` is the one place the adjuster-vs-capacity split is declared; read it rather than testing reason strings inline.

12. **`needs_manual` items are UNPRICED — RCV and ACV arrive `null` and the cell is simply BLANK and editable.** The old "$5k / special-limit approval gate" is **dead** — if Kevin finds solid comps it auto-prices the item regardless of dollar amount (a $10k sofa prices normally). Kevin only refuses to price when `status === "needs_manual"`, and then `rcv`/`acv`/`tax`/`depr$` are `null` (derived cells render "—" and contribute 0 to totals). **No pills, no "Appraisal req'd"/"Low sample"/"No comps" badges, no Approve button, no action buttons in the cell** — the adjuster just types the price into the empty RCV cell like any other. `manual_reason` still travels on the payload for the audit log and the item drawer, but it is not surfaced as a badge in the grid. Entering a value sets `valuationBasis: "manual"`, clears `needsManual`, tags the row **Manual**, and exposes the `+` affordance to attach a proof URL. Amber `specialLimits` row-highlighting still exists as a coverage-cap cue, but it is **not** a blocker and **not** the same thing as `needs_manual`. Seed data: `data.jsx` flags all special-limits rows `manual_class`, plus two low-conf apparel rows as `low_sample`/`no_comps`.
13. **Straight-line is the DEFAULT depreciation method.** `depr% = min(round(age ÷ useful-life × 100), 90)` — the 90% cap retains a salvage floor. `USEFUL_LIFE` (class → years, in `data.jsx`; `null` on Jewelry/Firearms/Fine Arts/Furs = no auto-depreciation, never "0 years" — live source is `GET /v1/depreciation-rules`, fetch not retype) drives it, and `buildWorksheetRows` **stores** straight-line values so the worksheet, export, and PDF all agree on one method. The bracketed `DEP_TABLE` (class × age bracket) remains as an alternate a carrier profile can select; `Custom` = preparer-entered. The PDF (`pdf-inventory.jsx`) discloses the method in the meta grid + Preparation notes and recomputes figures per method. `needsManual` rows stay 0% (unpriced, rule 12).
14. **Personal property limit, never "Coverage C" hardcoded.** Policies name contents coverage differently (Coverage C, Personal Property, Contents, Coverage B for renters, Business Personal Property). The claim carries BOTH a `ppLimitLabel` (picked at intake from the insured's declarations page) and a `ppLimit` dollar amount, plus `alreadyClaimed` for prior contents payments. The `PolicyLimitMeter` (accent → amber at 80% → red over limit) was dropped from BOTH the worksheet totals bar and the claim-overview stats for space — both print exact dollar amounts (`fmtUSD`, two decimals). The label/limit data (`CLAIM_PP_LIMIT`) still travels on the claim for the export summary. Never print a coverage letter as though it were universal.
15. **Claims can always be archived OR permanently deleted — it's the customer's account.** Archive is reversible, keeps everything (items, photos, exports, audit log), and stays reachable under the **Archived** filter on the claims dashboard. Delete is permanent and requires typing DELETE. Kevin does not gate either action for compliance reasons: **Kevin is a platform for building content lists, not a compliance system.** Retention/record-keeping obligations belong to the carrier and the adjuster, not to us.
16. **Kevin never blocks an export on editorial readiness.** The export modal (06) surfaces what needs attention — unpriced rows, missing model numbers, special-limits classes — and the adjuster decides whether to proceed; the download buttons stay live. `63-Export-failed.html` is a **technical** failure state only (generation error, storage read failure, share-link mint failure), with a retry and a reference ID. Never reintroduce a "not ready yet" gate, a class/cap review requirement, or an "Export anyway" escape hatch: Kevin is a platform for building content lists, not a compliance system (see rule 15).
17. **The "not an appraisal" valuation disclaimer lives in the Terms of Service (§4), not on exported PDFs.** `legal-hub.jsx` → `TERMS_SECTIONS`. Don't stamp disclaimers on every inventory — most exports go straight into Xactimate/XactContents anyway.
18. **Useful life and content class are internal to the depreciation math — never adjuster-facing columns on an export.** Xactimate/XactContents-parity columns are `# · Room/Area · Qty · Description · Make·Model · Unit Cost · Ext. Cost · Sales Tax · RCV + Tax · Age · % Depr. · $ Depr. · ACV`. Age prints as a bare number (`2`, not `2y`) so it lands numeric in Excel, and **tax is shown per line item** (`(rcv × qty) × taxRate`), not only as a claim total.
19. **Storage & fair use — unlimited claims, generous storage, nothing ever deleted.** Photo storage and line items are the two metered dimensions — storage because it is the standing cost, items because each one costs ~$0.08 to produce (see rule 9 for the 2,000/month allowance and $0.20 overage). Neither ever gates work. Policy, surfaced in Billing settings (`settings-pages.jsx` → `StorageUsageCard`) and derived in `window.KEVIN_STORAGE` (`data.jsx`): Pro includes **500 GB active storage**; **closed claims tier to archived storage after 90 days** (still fully accessible, marginally slower first load) — that tiering is the COGS lever, *not* deletion or claim caps; going over the pool triggers an **email first, never a mid-claim lockout**, then **$19/mo per additional 500 GB**. Claims stay unlimited — it is items, not claims, that carry an allowance (rule #9) and **nothing is ever deleted to reclaim space** — it's the customer's data (rule #15). The used figure is DERIVED from the account's actual photo counts × `STORAGE_AVG_PHOTO_MB` (4.2 MB, typical iPhone field capture) — never a typed-in GB literal.
20. **The frontend is DUMB about valuation — the backend is the source of truth.** No component may intercept, route, or categorize an item for pricing. The API returns each item already priced or flagged `needs_manual` with a `manual_reason`; the UI's only job is to render the state the payload carries. Concretely: **never** derive `specialLimits`, `needsManual`, or a valuation basis from `cat` at render time (`SPECIAL_LIMITS.has(row.cat)` inside a component is a bug — read `row.specialLimits`); no class→source routing table, no "classes Kevin auto-prices" scope list, no per-class manual/auto rules on any settings or marketing screen. `SPECIAL_LIMITS` in `data.jsx` exists **only** to stamp the mock payload once (standing in for the API response) — it is not a runtime lookup. Group headers and rollups aggregate the rows' own flags (`items.some(r => r.specialLimits)`). This extends to the math: the frontend does not compute depreciation either — see the worksheet section. `DEP_TABLE` / `USEFUL_LIFE` / `getDepFor` live in `data.jsx` **only** because that file stands in for the backend; no component may call them to derive a displayed value.
21. **Large-dump ingestion is chunked client-side; rejections are explicit; staging thumbnails are lazy.** The adjuster selects all 300+ photos and clicks once — the FRONTEND chunks it (`KevinAPI.planUploadChunks`, **20 files / 65 MB** per `POST /v1/claims/{id}/staging/photos` — a CLIENT-side choice, not a server constraint: the server caps 50 photos/request and 15 MB/file with NO total-bytes cap, but the GATEWAY is the real limit: a ~160 MB chunk ran past 2 minutes and returned a **502**, the client retried, and the already-saved photos came back as duplicates) so a 1 GB payload never hits a gateway timeout; a **413** halves that chunk and retries it alone. Each response carries `rejected: [{filename, reason, detail}]` where **`reason` is a CLOSED enum** (`unsupported_format` · `empty_file` · `oversized_photo` · `oversized_dimensions` · `undecodable_image` · `duplicate` · `storage_error` — no `truncated_file`; a truncated upload arrives as `empty_file` or `undecodable_image`) mapped to copy by `REJECT_COPY` in `intake.jsx` — never print a raw code, branch on `reason` and display `detail`. Every ack carries `max_upload_bytes` for the client-side pre-check. The upload also takes an optional per-BATCH `room` field (never per-photo — two rooms = two requests) that rides to the worksheet's Room/Area column; **the capture flow must send it** or the column stays null. **`duplicate` is a SUCCESS** reported on ONE channel (a `duplicate` reason code in `rejected[]`, never a parallel `duplicates:[]` array) — it means the photo is already stored in the session, and it arrives in volume after a 502 retry; counting those as failures reported "196 failed" for photos that were all safe, so duplicates reconcile into the stored count and never reach the red panel. A failed photo is never silently dropped, BUT `undecodable_image` is **quiet**: that is how iOS `.AAE` edit-sidecars arrive, so they collapse into one info line rather than a red failure panel — alarming someone over invisible OS files whose shoot was fine is a bug. A `.zip` is **expanded in the browser** (`KevinAPI.expandZip`, zip.js) with `__MACOSX/`/`.DS_Store`/`Thumbs.db` filtered locally; the archive is never posted whole. **Extraction is sequential, upload is parallel** — a ZipReader holds a file position, so concurrent `getData()` on one reader corrupts the stream ("Overlapped entries / possible zip bomb", which reads like a malicious archive but is our own concurrency bug). Use `for..of` with `await`, never `Promise.all`; if extraction must parallelise, every worker constructs its own ZipReader over its own BlobReader slice.

22. **A claim has MANY ingest sessions — a second drop APPENDS, never overwrites.** `CLAIM_SESSIONS` / `CLAIM_INGEST` in `data.jsx`. Five rules: (a) **staging is scoped to the current session only** — prior batches are never re-staged; (b) **line numbering continues** (session 2 starts at #0045) and existing rows are NEVER renumbered, because an export already sent to a carrier cites those numbers; (c) **dedupe hashes span the whole claim, not the batch** — re-dropping yesterday's folder must resolve to duplicates, not new items; (d) the worksheet gains a **batch filter** (default all) that changes what you see, never what exports; (e) claim photo/item counts are **sums over PROCESSED sessions**, never literals — photos sitting in staging have produced no line items yet and must not inflate the claim (`CLAIM_INGEST.pendingPhotos` carries those separately, for storage rollups only). The canonical demo claim therefore still reads 60 photos → 57 items on every surface while session 2 is in staging, and totals/policy-limit meter re-derive from the row set. Once exported, a claim is a legal artifact: a later ingest does not reopen it — the next export is simply a new version, and v1 must still open as v1. Staging's poll carries **no signed image_url** (300 signed URLs every 4s crashed the server): an IntersectionObserver batches visible set ids into `GET /v1/staging/photos/thumbnails?ids=` capped at 100 ids per request, cached per id, skeleton until it lands. Don't reintroduce per-file manual uploads, silent drops, or image_urls in the poll. **Loose photos** (`group_key = NULL`) surface in an amber **unassigned tray** pinned above Process — but ONLY once their extraction completes; a photo still extracting has not been tried yet and must stay in the pending state. **Loose photos render as ordinary single-photo cards in the grid** (amber edge) so merge/note/exclude work through the controls the adjuster already knows — there is no separate assign sheet. Assigning one by hand therefore goes through the normal set-merge, `POST /staging/groups/merge` (mixed selectors; it mints a new `group_key`, so never cache one across the call, and pass `kind` explicitly or a context set is silently converted). **Cluster remaining** (`POST /staging/cluster/remainder`) groups just those and APPENDS — never `/staging/cluster`, which rebuilds the session and discards manual merges. Process is **never blocked**: the label states the cost, one confirm makes it deliberate, and excluded photos stay on the claim — in property claims evidence is **excluded from the worksheet, never deleted**.
23. **Ingestion = backend proposes, adjuster decides, frontend submits.** Order is fixed: upload → backend pre-clusters photos into **proposed photo sets** (timestamp + AND-gate) → staging renders the proposal (`photo-staging.jsx`). **Staging is a PRE-Vision surface: it must never show identified data.** No item names, no makes/models, no rooms, no "wide shot + model plate" reasoning, no special-limits flags — the clusterer only knows capture time and EXIF proximity. Cards show `Set 01` + timestamp + filenames + raw metadata ("2 photos · 4s apart"), and `skip` is set by the ADJUSTER, not proposed. The tally counts **photo sets** (50 photos → 47 proposed sets), never line items — the item count isn't known until Vision runs → the adjuster **merges / splits** sets and attaches an optional **set note** (PATCH `…/staging/groups/{group_key}/note`, max 300 chars; per-photo notes on mobile also allow 300). **Set notes carry `note_source` ∈ `derived` | `adjuster` — branch on it, never on the text.** `derived` = the backend's fusion of member photo notes (`merge_notes`: " | ", deduped, 120-char cap — NEVER re-concatenate client-side; `mergeUserNotes` in `data.jsx` exists only to mock it) and renders as read-only context; `adjuster` = human-written, the one editable slot; sending `null` drops the override and the derived summary returns. What a set note actually does: at `/staging/process`, on a set with NO usable query (vision fell back, no barcode) an ADJUSTER note becomes the search query — a derived note never does; on a validated set it is commentary. To re-steer identification, use the per-photo note and re-run clustering → **Staging is saved INCREMENTALLY — Process posts NO body.** Every merge, split, note, skip and exclusion is written to the backend the moment the adjuster makes it (merge → `POST …/staging/groups/merge`; set note → `PATCH …/groups/{key}/note`; **there is NO skip at process time** — excluding a set = reclassify it: `PATCH …/staging/groups/{key}` `{kind:'context'|'duplicate'}`, which promotes to zero line items). Hitting Process calls `POST /v1/claims/{id}/staging/process` with no payload — the backend promotes whatever state the database already holds. There is no `submitPhotoSets` and no monolithic photo_sets payload; don't reintroduce one. A lone photo is a "set of 1". Notes are **pre-processing only** — they steer Vision identification, never price, and a misidentification after the run is corrected by editing the worksheet row, NOT by a second Vision call. The same `user_note` structure exists on mobile capture (`mobile-capture.jsx`, note bar + bottom sheet, attached to the current capture set). **Mobile review (`mobile-review.jsx`) attaches notes PER PHOTO** — sets do not exist until the clusterer runs — so when a proposed set contains photos with different notes they are **concatenated with ` | `** (distinct values only, truncated to 120 chars with an ellipsis) and the merged string lands in staging's single editable note slot. Never keep only the first note and never silently drop one: the adjuster typed it on site. `mergeUserNotes()` in `data.jsx` is the one implementation; staging's set-merge calls the same helper. **Splitting is the mirror rule: a merged note stays on the FIRST child only** (`note`/`fromField` are cleared on children 2..n) — copying it onto every photo fabricates notes the adjuster never wrote, and a note naming the wrong brand steers identification away from the right answer. Nothing is lost: the note stays on screen and editable. UI label is **"Additional identification"** — not "steers identification".

24. **Written inventories import WITHOUT photographs — and never through staging.** `written-import.jsx`, page 75. Total-loss lists arrive as PDF/CSV/XLSX; a described item prices exactly like a photographed one (RCV = median of live retail comps), just without brand/model precision. Staging exists to turn photos into items via cluster → review → promote, so it has nothing to do here: **a written row already IS a line item** and goes straight to the worksheet. Flow is parse → map → preview → import, and **the first three create nothing**. Rules: (a) parsing is **server-side** (`…/items/parse`) because real inventories are PDFs — never add a browser parser; (b) `suggested_mapping` is partial by design, and the mapping step is shown even when pre-filled; (c) `room` stays its own field — the description doubles as the search query, so a stray room name changes the search; (d) rows flagged `likely_heading` are **pre-selected for removal, never auto-dropped** — a heading left in prices as property; (e) **`price:false` on `…/items/bulk` is NOT a dry run** — it still inserts every row; the only dry run is `…/bulk/preview`; (f) import is capped at **500 rows per request** and resumes from a failed chunk; (g) confirmation states `estimated_searches` (two vendor searches per priced item), not the row count.

## Worksheet — the centerpiece

`components/worksheet.jsx` is the core screen. Columns (in order):
`☐ · # · Room/Area · Qty · Description · Make/Mfr · Model # · Content class · Unit Cost · Ext. Cost · Sales Tax · RCV + Tax · Age · % Depr. · $ Depr. · ACV · source-link`

**Money chain (locked — SERVER-OWNED).** `rcv`/`acv` are **per-unit, pre-tax**. The worksheet and export money columns are the tax-inclusive line totals the API returns and the UI reads verbatim: `tax` = rcv × qty × tax_rate · `rcv_total_incl` = rcv × qty + tax · `depreciation_amount` = round(rcv_total_incl × depreciation_pct, 2) — depreciation applies to the TAX-INCLUSIVE RCV · `acv_total_incl` = rcv_total_incl − depreciation_amount. `depreciation_pct` is a **fraction** (0.30 = 30%). Items land from processing at **age 0 → ACV = RCV**; the adjuster enters `age_years`, which triggers the server recompute. Never recompute these client-side — `computeACV()` was deleted for exactly that reason. Superseded chain, for reference only: `Ext. Cost = Unit Cost × Qty` → `RCV + Tax = Ext. Cost + (Ext. Cost × taxRate)` → `$ Depr. = Ext. Cost × % Depr.` → **`ACV = Ext. Cost + Tax − $ Depr.`** So the columns foot left-to-right and tax IS inside ACV. One implementation: `computeACV()` in `worksheet.jsx`; `REYES_TOTALS` in `data.jsx` and `pdf-inventory.jsx` must match it. Ext. Cost / RCV + Tax / $ Depr. are read-only derived cells — editing happens on Unit Cost, Qty, Age, % Depr.

- The **# column** click opens the photo lightbox (the thumbnail column was removed — don't reintroduce it).
- **Room/Area** is a **free-text input** (not a dropdown — houses have arbitrary room names). Filterable.
- **Content class** is a searchable dropdown of `PCS_CATEGORIES` (in `data.jsx`).
- **Depreciation is NEVER computed in the frontend.** Changing content class or age sets `depPending` on the row: the Depr. cell goes **read-only with a spinner** and the value renders as "—" until the server answers (`window.KevinAPI.recalcDepreciation(id, {cat, age})` — the mock API boundary in `data.jsx`, faked with ~420ms latency). The returned percent is applied and the cell flashes mint. Client-side `getDepFor()` recalc was **removed** — JS rounding could disagree with the backend and make the worksheet contradict the exported PDF. Direct edits to Depr. set `depManual=true` and skip the server call. `needsManual` rows never recalc.
- **Resizable columns** (Google-Sheets style): drag header boundaries; double-click to reset. Driven by `--row-cols` CSS var.
- **Filter** popover: Room text input + barcode/special-limits/low-confidence/high-value toggles. **Group by class** toggles a sectioned view with subtotals. **Search** matches desc/mfr/cat/model/room.
- **Virtual scroll:** windowed rendering for the 44 rows (scales to 500+) (`startIdx`/`endIdx`/overscan).
- **Dockable item drawer.** Clicking the **#** column opens the item drawer (photo · editable fields · Edit & re-price · live comps · LKQ note · computed totals). The header **pin** toggle docks it to a 440px right rail beside the grid, where it stays open and re-syncs to whichever row you click — plus/next arrows still work. Unpin returns it to the modal. There is **one** worksheet: the split/grouped/dense variants (`worksheet-variants.jsx`, pages 07–09) were **deleted**; grouping lives in the toolbar's Group-by-class toggle. Don't reintroduce parallel grids.

Row data shape is generated by `buildWorksheetRows(n)` in `components/data.jsx` — read that file for the canonical item object.

### No-dead-ends rule (READ before handoff)
Claude Code will NOT infer intent for an undocumented static control — an inert button stays inert or gets invented behavior. So intent must be explicit. Two safeguards:
1. **Default contract:** every actionable control (button, link, menu item, row) must EITHER do something visible in-prototype OR have its intended production behavior recorded in `INTERACTIONS.md`. A control that is visually-only AND undocumented is a bug, not a design choice.
2. **`INTERACTIONS.md` is the wiring manifest** — per page, each control → {prototype behavior, production target/endpoint}. When you add or change a control, update that file in the same edit. Backend agent: treat `INTERACTIONS.md` as the source of truth for what each control must do; anything labeled "static (visual)" there is intentional, anything not listed should be flagged back, not guessed.
